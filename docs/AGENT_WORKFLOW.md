# Agent 工作流程

## 角色与责任

这里的角色是工作分工，同一个 agent 可依次担任。默认单 agent 开发，不启动常驻多 agent 系统。

| 角色               | 输入                 | 输出                         | 验收责任             |
| ------------------ | -------------------- | ---------------------------- | -------------------- |
| 产品负责人（用户） | 目标与玩家反馈       | 玩法范围、优先级、美术方向   | 对外体验和发布决定   |
| 规划/架构          | 产品草稿、任务看板   | 任务卡、依赖关系、ADR        | 范围明确、能被验证   |
| 实现               | Ready 任务、接口契约 | 代码、必要测试、文档         | 满足验收条件         |
| 评审/测试          | diff、验收和证据     | 缺陷列表、验证记录           | 回归、平台兼容和风险 |
| 发布维护           | 已验收候选版         | 版本记录、构建信息、发布记录 | 可追溯、可回退       |

## 一次任务的闭环

1. **接手**：读约定、看板、任务卡，检查工作区，确定分支和文件归属。
2. **澄清**：填好任务目标、非目标、验收和依赖；缺产品决定的工作保持 Proposed。
3. **实现**：一项任务一个 PR；优先完成最小可运行纵向切片，避免同时重写多个系统。
4. **验证**：执行质量门禁和有意义的行为测试；平台相关变更附工具/真机证据。
5. **评审**：检查架构、资源释放、失败路径、依赖、素材、体积及版本记录。
6. **交付**：更新看板；记录 commit、命令结果、未验证项和恢复工作所需信息。

状态：`Proposed → Ready → In Progress → Review → Done`；阻塞使用 `Blocked` 并注明依赖。
Ready 需要明确验收与可用输入。Done 要求所有约定验收都满足；未跑的验收不能打勾。
若任务只有本地工程验收，不应因未来账号接入未完成而无限挂起；把后续依赖分成独立任务。

## 可直接使用的任务提示词

```text
读取 AGENTS.md、docs/tasks/BOARD.md 和任务卡 TASK-XXX。
先确认工作区状态与本任务验收，在独立短分支完成范围内的修改。
维持架构边界，补充必要的行为测试；执行适用检查并记录真实证据。
更新任务卡与相关文档，给出改动、验证结果、风险和下一步。
遇到缺失输入时先完成不依赖它的工作；不要把假设当成已确认需求。
```

## 并行与交接

仅在用户明确要求并行时拆出独立模块。拆分前固定共同接口、各自负责文件和集成顺序。
每名实现者使用独立 worktree/分支，禁止多人同时修改锁文件、同一配置或公共端口。
主 agent 负责集成后的完整验证；各分支分别通过不代表集成后通过。

暂停或上下文交接时填写 [交接模板](templates/HANDOFF.md)，至少记录工作区、提交、未提交修改、
已验证项、阻塞点和下一条具体动作。不要仅写“基本完成”。
