# 测试与验收策略

## 自动检查

`npm run verify` 顺序执行：格式 → 源码及测试类型 → 分层约束 → 策划静态一致性 → AppID隔离 → 单元测试 → 构建 → 包检查 → 产物冒烟。
每一步失败立即停止。测试 Node 版本建议与 CI 的 24 保持一致。

| 层级     | 当前覆盖                                            | 能证明什么                                     |
| -------- | --------------------------------------------------- | ---------------------------------------------- |
| 单元     | 重复启动、ID=0 取消、帧间隔、恢复、异常后重启       | 帧循环可控且后台时间不累加                     |
| 工程约束 | 分层导入、平台全局、显式随机/时间、发布配置         | 常见边界违规或无效配置会被阻止                 |
| 产物契约 | 在没有 DOM/Node 全局的模拟微信环境执行 game.js      | 构建入口、绘制、触摸、DPR、前后台基本契约成立  |
| 包检查   | 配置、版本、入口哈希、map、敏感文件名与内部体积预算 | 常见打包错误被发现；不是全面秘密扫描或官方审核 |

玩法阶段补规则测试：碰撞边界、胜负、计分不重复、重开清状态。
只有引入存档/音频/网络后，才增加迁移、生命周期和失败恢复测试。

## 必须人工或真机完成

- 微信开发者工具：导入 dist 后不报错，菜单与玩法可见，触摸反馈，隐藏恢复没有重复循环。
- iOS / Android：冷启动、触摸、安全区、不同屏幕、切后台/锁屏/恢复。
- 有音频后：静音、来电中断、恢复策略；有存档后：清缓存、升级、损坏数据。
- 可玩版本：连续至少 5 分钟测试，记录帧时间与内存趋势；反复重开和后台恢复。
- 弱网/断网仅在加入网络能力后进行；不添加无实际功能的虚假验收项。

使用 [设备测试模板](templates/DEVICE_TEST.md)。记录真实结果、版本、commit 和证据路径；
不将 mock、Node 测试或页面截图记为微信真机通过。

## 发布验证

`npm run verify` 生成开发包；执行 `npm run build:release` 才生成并检查压缩发布候选包。
生成发布包之后再次执行 verify 会将 dist 改回开发包；上传前检查 build-info 的 mode 和 commit。
工具和真机验收必须基于最终候选包，不只在开发模式测试。

当前版本实测与未验证项见 [v0.2试玩记录](testing/V0.2_PLAYTEST.md)。完整脚本试跑使用`npm run simulate`，不能将机器人通关解释为平衡或真人乐趣通过。
